## ADDED Requirements

### Requirement: Telegram configuration uses backend data
The system SHALL load Telegram bot connections, destinations, feature settings, and market analysis schedules from the documented Telegram backend APIs instead of local fixtures.

#### Scenario: Authorized section data is loaded
- **WHEN** a user opens the Telegram configuration workspace with a Telegram read permission
- **THEN** the system fetches only the Telegram collections allowed by that user's read permissions and renders those sections from backend responses

#### Scenario: Missing section permission does not break page
- **WHEN** a user has access to at least one Telegram read area but lacks another Telegram read permission
- **THEN** the system keeps the workspace available and shows an access-limited or disabled state for the section the user cannot read

#### Scenario: Backend data replaces fixture data
- **WHEN** Telegram backend responses are available
- **THEN** the system displays real bot connection, destination, feature setting, and schedule metadata rather than static review rows

### Requirement: Telegram bot connections are API-backed
The system SHALL support Telegram bot connection management using the backend multi-bot contract.

#### Scenario: Bot connection list renders real records
- **WHEN** `GET /telegram/bot-connections` succeeds
- **THEN** the bot section shows the returned bot labels, usernames, statuses, validation metadata, and available row actions

#### Scenario: Bot token is only submitted on create
- **WHEN** the user creates a Telegram bot connection
- **THEN** the system submits `botToken` and optional `displayLabel` to `POST /telegram/bot-connections` and does not display the token after creation

#### Scenario: Bot label can be updated
- **WHEN** the user updates a bot connection label
- **THEN** the system submits `displayLabel` to `PATCH /telegram/bot-connections/{id}` and refreshes Telegram configuration data after success

#### Scenario: Bot destructive actions are confirmed
- **WHEN** the user disables or removes a bot connection
- **THEN** the system requires an `AlertDialog` confirmation, calls the matching backend endpoint, shows mutation feedback, and refreshes the Telegram workspace

### Requirement: Telegram destinations and link tokens are API-backed
The system SHALL support destination listing, link-token generation, update, disable, and removal through Telegram destination APIs.

#### Scenario: Destination list renders real records
- **WHEN** `GET /telegram/destinations` succeeds
- **THEN** the destination section shows the returned destination label, chat type, chat metadata, bot relationship, status, and row actions

#### Scenario: Link token command is generated by backend
- **WHEN** the user starts the destination linking flow for an active bot connection
- **THEN** the system calls `POST /telegram/destinations/link-token` with `botConnectionId` and displays the returned `startCommand` and `expiresAt`

#### Scenario: Destination verification is refreshed explicitly
- **WHEN** the user completes the `/start <token>` command outside the app
- **THEN** the system provides a way to refresh destination data instead of creating an optimistic destination locally

#### Scenario: Destination mutations refresh data
- **WHEN** the user updates, disables, or removes a destination
- **THEN** the system calls the matching backend endpoint, shows mutation feedback, and refreshes the Telegram workspace

### Requirement: Telegram feature routing is API-backed
The system SHALL support Telegram feature route display and update through `GET /telegram/feature-settings` and `PUT /telegram/feature-settings`.

#### Scenario: Feature settings render for current workspace
- **WHEN** feature settings are loaded
- **THEN** the system displays `ECONOMIC_CALENDAR_ALERT`, `MARKET_NEWS_ALERT`, and `SCHEDULED_MARKET_ANALYSIS` for the current workspace using backend state where available

#### Scenario: Route update requires a valid destination
- **WHEN** a user updates a feature route
- **THEN** the system sends `featureKey`, `workspaceId`, `destinationId`, and `enabled` when available, and blocks mutation controls when no active destination can form a valid request

#### Scenario: Feature route switch remains scoped to enabled setting
- **WHEN** a user toggles a feature route
- **THEN** the system updates only that feature setting and does not imply bot, destination, or schedule reactivation

### Requirement: Scheduled market analysis schedules are API-backed
The system SHALL support scheduled market analysis schedule listing and management through Telegram schedule APIs while keeping the schedule surface nested under `SCHEDULED_MARKET_ANALYSIS`.

#### Scenario: Schedule list renders real records
- **WHEN** `GET /telegram/market-analysis-schedules` succeeds
- **THEN** the nested scheduled market analysis area shows schedule name, workspace, destination, timezone, local times, assets, status, and row actions from backend data

#### Scenario: Schedule form submits documented request
- **WHEN** the user creates or updates a schedule
- **THEN** the system submits `name`, `workspaceId`, `destinationId`, `timezone`, `localTimes`, and `assetIds` using the documented schedule request shape

#### Scenario: Schedule form uses current workspace context
- **WHEN** the user opens the schedule form
- **THEN** the system preselects or constrains workspace-dependent choices to the current workspace and its watchlist assets

#### Scenario: Schedule destructive actions are confirmed
- **WHEN** the user disables or removes a schedule
- **THEN** the system requires an `AlertDialog` confirmation, calls the matching backend endpoint, shows mutation feedback, and refreshes the Telegram workspace

### Requirement: Telegram API integration preserves frontend safety boundaries
The system SHALL keep backend-only Telegram webhook handling and Telegram Bot API update schemas out of the frontend configuration surface.

#### Scenario: Webhook endpoint is not user callable
- **WHEN** Telegram API integration is implemented
- **THEN** the system does not expose `/webhooks/telegram/{connectionId}` as a frontend action or control

#### Scenario: Server actions use authenticated fetch
- **WHEN** the frontend calls Telegram backend endpoints
- **THEN** those calls use `fetchAuthenticated()` from server-side actions and preserve the existing response-text parsing behavior

#### Scenario: Validation rejects malformed form input
- **WHEN** a user submits Telegram configuration forms
- **THEN** the system validates inputs with Zod before sending documented backend requests
