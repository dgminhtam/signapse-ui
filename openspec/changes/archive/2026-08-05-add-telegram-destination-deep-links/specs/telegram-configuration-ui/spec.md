## MODIFIED Requirements

### Requirement: Telegram destinations and link tokens are API-backed
The system SHALL support destination listing, link-token generation, Private and Group Telegram deep-link opening, update, disable, and removal through the existing Telegram destination APIs and bot-connection data.

#### Scenario: Destination list renders real records
- **WHEN** `GET /telegram/destinations` succeeds
- **THEN** the destination section shows the returned destination label, chat type, chat metadata, bot relationship, status, and row actions

#### Scenario: Link token command is generated by backend
- **WHEN** the user starts the destination linking flow for an active bot connection
- **THEN** the system calls `POST /telegram/destinations/link-token` with `botConnectionId` and displays the returned `startCommand` and `expiresAt`

#### Scenario: Private deep-link uses the matching bot and token
- **WHEN** the user has generated a link token for an active bot connection and activates the Private deep-link action
- **THEN** the system opens `https://t.me/<botUsername>?start=<token>` using the `botUsername` from the matching `GET /telegram/bot-connections` record and the token returned by `POST /telegram/destinations/link-token`

#### Scenario: Group deep-link uses the matching bot and token
- **WHEN** the user has generated a link token for an active bot connection and activates the Group deep-link action
- **THEN** the system opens `https://t.me/<botUsername>?startgroup=<token>` using the `botUsername` from the matching `GET /telegram/bot-connections` record and the token returned by `POST /telegram/destinations/link-token`

#### Scenario: Deep-link activation refreshes the workspace
- **WHEN** the user activates either Telegram deep-link action
- **THEN** the system opens the external Telegram link in a new target and refreshes the Telegram configuration workspace without creating an optimistic destination

#### Scenario: Destination verification is refreshed explicitly
- **WHEN** the user completes the `/start <token>` command outside the app
- **THEN** the system provides a way to refresh destination data instead of creating an optimistic destination locally

#### Scenario: Deep-link actions are guarded when required data is missing
- **WHEN** the generated token or the matching bot username is unavailable
- **THEN** the system does not expose an actionable malformed Telegram deep-link and keeps the user-visible fallback/error state localized

#### Scenario: Changing the bot invalidates the displayed token
- **WHEN** the user changes the selected bot after a link token has been generated
- **THEN** the system clears the prior token and requires a new link-token request before exposing Private or Group deep-link actions

#### Scenario: Destination mutations refresh data
- **WHEN** the user updates, disables, or removes a destination
- **THEN** the system calls the matching backend endpoint, shows mutation feedback, and refreshes the Telegram workspace
